## Phase 0 follow-up — Expo Go crash fix (2026-08-06)
- Built: Fixed the app immediately crashing (Expo Go force-closes, no error in
  Metro) after the Android bundle completes. Root cause is a known upstream bug
  (expo/expo#48390, iOS variant #48418): the SDK 57 template resolves
  `react-native-reanimated@4.5.1` + `react-native-worklets@0.10.1`, but both
  released Expo Go 57 clients (Android 57.0.2, iOS 57.0.5) bundle 4.5.0/0.10.0
  natively. The JS/native mismatch makes worklets runtime init SIGSEGV on
  launch. Repro is template-level: even a bone-stock create-expo-app project
  crashes, so it was never our code.
- Files: `package.json`, `package-lock.json` (downgraded
  `react-native-reanimated` to 4.5.0, `react-native-worklets` to 0.10.0, then
  clean `npm install`).
- Decisions/deviations: Deliberately pins below what `npx expo install --check`
  expects (it now flags 4.5.1/0.10.1 as "expected"). Do NOT run
  `expo install --fix` or blindly upgrade these two — it reintroduces the
  crash until Expo ships an Expo Go 57.x with 4.5.1/0.10.1 (tracked in issue
  #48390). Alternative workaround in that issue (metro resolveRequest returning
  an empty module for react-native-worklets) was rejected: it disables
  worklets entirely; the pin keeps everything functional. Removing the two
  packages entirely was rejected too — expo-router declares
  `react-native-reanimated` as a peer dependency.
- Next phase should know: If the device is a Galaxy S24-family phone the bug
  report noted the crash hits there too (not device-specific though). After
  pulling this change, fully kill Expo Go (swipe from recents) before scanning
  again; stale worklets native code from the crashed session can linger in
  memory. When Expo Go ships 4.5.1/0.10.1 natively, revert to the SDK-expected
  versions with `npx expo install react-native-reanimated react-native-worklets`.
